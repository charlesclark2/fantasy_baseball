# Credence — repo guide for Claude Code sessions

## 🚨 WHICH APP TO EDIT — READ FIRST

Three things share confusingly similar paths. Two are live; one is dead.

- ✅ **UI / anything user-facing → `frontend/` ONLY** — the **Next.js** app (Vercel, auto-deploys on push to main).
- ✅ **API / backend → `app/backend/`** — the **live FastAPI** service (deployed to Lambda via `infrastructure/lambda/deploy.sh`; `app.backend.main` is the entrypoint). This is live — edit it for backend work.
- ⛔ **DEPRECATED legacy Streamlit UI → `app/streamlit_app.py`, `app/home.py`, `app/pages/`, `app/utils/`** — **not deployed, not the product. Do NOT edit** unless a task *explicitly* names "legacy Streamlit."

**Footgun (this is what bit a session on 2026-06-18):** the dead Streamlit UI files sit at the **top of `app/`, right next to the live `app/backend/`**, and Next.js has its *own* router dir at `frontend/app/`. So `app/` is **half-alive**: `app/backend/` = keep; everything else in `app/` = legacy UI = don't touch. "The app's UI" is **always `frontend/`**, never `app/home.py` / `app/pages/`.

**First action in any app/UI session:** run `cat frontend/package.json` and confirm Next.js (`"next"` in deps, `"dev": "next dev"`). If you're doing **UI** work and find yourself in `streamlit_app.py`, `st.set_page_config`, `app/home.py`, or `app/pages/*.py`, **STOP — wrong place → go to `frontend/`.**

## 🌿 PER-SESSION BRANCHES + PUBLISH-FROM-MERGED-DEV (2026-08-02 — TRIAL, to fix cross-session collisions)
**WHY:** concurrent sessions kept colliding — NF1.5b + NF3.4 both edited `export_draft_board_json.py` / shared TS in ONE working tree (a silent stomp + a near-miss premature publish). There are TWO collision CLASSES, and each needs its own rule:
1. **CODE collision → EACH SESSION WORKS ON ITS OWN BRANCH.** FIRST action of every session: `git checkout dev && git pull && git checkout -b <session-branch>` (name it for the story, e.g. `nf3.2-receipts`). Commit + push to THAT branch ONLY. ⛔ NEVER commit/push to `dev` or `main` directly. When the story is done + CI-green, the closeout hands the operator a PR (branch → `dev`); the operator merges. A second session that shares files then REBASES on the merged `dev` — the conflict is EXPLICIT + reviewable, not a silent working-tree stomp. (This supersedes the old "sessions don't commit / hand back a `git add` list" model, which assumed one shared tree.)
   - ⚠️⚠️ **A BRANCH ISOLATES COMMITS, NOT THE WORKING TREE — concurrent sessions SHARE ONE CHECKOUT unless a session uses `git worktree` (INC-39 + NF-D19, 2026-08-02, both hit it the SAME day).** Two Claude sessions running against the same repo dir share ONE `.git` working tree, so a parallel session can `git checkout` and switch HEAD OFF your branch mid-task, and its uncommitted in-flight edits to UNRELEASED files sit in YOUR `git status`. The per-session-branch rule prevents a bad *commit*, not a mixed *tree*. **CONSEQUENCES + RULES: (a) re-run `git branch --show-current` IMMEDIATELY BEFORE EVERY COMMIT — HEAD may have moved since you branched; (b) stage ONLY your story's explicit paths (`git add <path> …`), ⛔ NEVER `git add -A`/`git add .` — that sweeps another session's mid-edit into your commit; (c) a test failure in a file you don't recognise is probably another session's mid-edit, NOT your bug — re-run it a minute later before chasing it (INC-39 hit exactly this: 7 core-shard failures in an untracked file that passed on re-run); (d) ⭐ the clean isolation is `git worktree add ../<session-dir> -b <branch>` off `dev` — a SEPARATE working dir so another session's HEAD-switch can't touch yours (NF-D19 did this to isolate from a session mid-task on `mh2.1-wide-window-retrain`); prefer it whenever you know another session is live.**
   - ⚠️ **BUT A FRESH `git worktree` CANNOT RUN THE SLOW GATE — `dbt/target/manifest.json` is gitignored, so it is ABSENT in any new worktree, and `pipeline/__init__.py` reads it AT IMPORT → ~20 sensor tests die at COLLECTION on any fresh-worktree branch (NF-D18, 2026-08-03).** This is a WORKTREE artifact, NOT a code regression — prove it by running the SAME slow gate in a control worktree at plain `dev` (it fails the identical ~20), don't report a phantom regression. The FAST gate is immune by design (it never imports `pipeline` — the E11.23 rule). ⇒ run the SLOW gate from the MAIN checkout (or symlink `dbt/target/manifest.json` into the worktree), and know that "20 sensor tests fail in my worktree" is expected, not your bug. ⭐ And the shared-tree hazard bites from BOTH directions: a CONVENIENCE COMMIT on your branch can SWEEP UP unrelated doc files + untracked artifact dirs belonging to OTHER sessions (NF-D18 swept 4 doc files + an artifact dir) — which is exactly why the `git add <explicit paths>` / never-`git add -A` rule is load-bearing; stage your story's files by name, never the tree.
   - ⭐⭐ **THE MORE DANGEROUS SIBLING — A FRESH WORKTREE CAN PRODUCE A FALSE *PASS*, not just a false failure (pre-draft board regen, 2026-08-03): an ON-DISK artifact-PRECEDENCE bug CANNOT be validated in a worktree, because the gitignored legacy artifact that TRIGGERS it is exactly what a fresh worktree LACKS.** The board exporter's `resolve_board` preferred a legacy `e7_13_prospect_board_comps.csv` (the pre-E8.1 export path) over the freshly-built board; verifying the publish end-to-end in a fresh worktree PASSED (no legacy file there) while PROD — which had a stale Aug-2 copy — silently published a 2-day-old board (moved prod BACKWARDS an hour after a good publish). Same NF-D18 mechanism (worktree lacks the gitignored artifact) facing the OTHER way: there a phantom FAILURE, here a phantom PASS — and the pass is worse because it ships. **RULE: any logic that reads/prefers an ON-DISK artifact (a source-precedence order, a "first existing candidate" pick, a cache/legacy-file fallback) CANNOT be validated in a fresh worktree — the worktree's CLEAN state HIDES the bug. Test it in a checkout that HAS the legacy/artifact files (the MAIN checkout, or copy them in), and always LOG the chosen path + mtime so a wrong pick is visible.** ⭐ SIBLING ROOT-CAUSE: **a "PREFERRED-SOURCE" constant is a TIME BOMB once the build STOPS WRITING that source** — E8.1 made native comps the build output but left the exporter PREFERRING the legacy `BOARD_WITH_COMPS` path, so any checkout that ever ran the old path keeps its stale file forever and the exporter silently prefers it (the "documented ≠ actually served" / stale-preference class). **When a build stops emitting an artifact, grep every CONSUMER's source-preference and repoint it; a preference pointing at a no-longer-written file is a silent-staleness bomb.** (Fixed: prefer a comps-carrying candidate, then NEWEST by mtime; a newer-but-comp-less candidate is passed over with a loud WARNING. Board regen shipped PR #564 org-correction + #566 exporter-fix, both merged; draft ran off the correct 1,459-row board.)
   - 🖥️⭐ **THE MAIN `dev` CHECKOUT IS RESERVED FOR THE OPERATOR + PM-DOC EDITS ONLY — EVERY WORK SESSION RUNS IN ITS OWN OPERATOR-CREATED `git worktree` (2026-08-03, after E8.3 + NF-D17 BOTH worked directly on the shared `dev` tree despite an inline branch FIRST-ACTION).** The failure mode is NOT a bad commit — sessions edit files in whatever checkout they're launched in and do NOT self-isolate, so an inline prompt instruction doesn't hold, and a commit-hook can't catch "editing without committing" (and would block the operator's own `dev` work). ⇒ ISOLATION IS OPERATIONAL, NOT IN-SESSION: the **OPERATOR creates the worktree BEFORE handoff — `git worktree add ../<story> -b <story-branch> dev` — and launches the session in THAT directory**; the session then physically cannot touch the main `dev` tree. The main `dev` checkout is edited ONLY by the operator (pulls/merges) + PM catalog/doc recordings; a session never works in it. This makes a session's "did it branch?" behaviour irrelevant AND protects PM edits on the main checkout from being wiped by a session's `git checkout` (exactly how NF-D17's first draft was lost).
   - ⚠️ **A `git show origin/<branch>` / remote-ref read can RACE the operator's merge and read a STALE ref (INC-39, 2026-08-02).** A session briefly told the operator "the box looks like it's on an un-merged branch" off a `git show origin/main` that raced a merge in flight. Before asserting deployed/branch STATE from a remote ref, `git fetch` first, and treat a single ref read as provisional — a stale read is a false alarm that costs operator time.
2. **LIVE-DATA / SERVING collision → `--publish` + `deploy.sh` ONLY FROM MERGED `dev`, NEVER FROM A WIP BRANCH.** ⚠️ **branches do NOT isolate prod** — there is ONE S3 api-cache bucket + ONE API Lambda, NO staging plane, and `--publish`/`deploy.sh` reach around git entirely. A session may BUILD + verify on its branch, but the actual `export … --publish` to prod S3 and `infrastructure/lambda/deploy.sh` are a DELIBERATE step AFTER the PR merges to `dev` — never fired mid-session off in-flight code. (The NF3.4 near-miss: a WIP re-export stamped the wrong `model_version`, one `--publish` from shipping another story's UNRELEASED board.) If a story's DoD needs a publish/deploy, the closeout LISTS it as an operator step to run POST-MERGE — the session does not do it.
⚠️ **NOT MECHANICALLY ENFORCED (know this):** `dev` has NO branch protection → the PR "gate" is the operator running both CI gates + reading the diff before merge; the branch gives the PLACE to do that, not automatic blocking. And the API-Lambda deploy-skew (backend needs `deploy.sh`; `frontend/` auto-deploys on `main`, NF-C0's lesson) is UNCHANGED — still remember it per feature.

### 🚦 LONG-RUNNING SCRIPTS (>2 min) → HAND TO THE OPERATOR, DO NOT RUN THEM YOURSELF (operator 2026-07-27 — sessions keep ignoring this)
**Any script/command you expect to run longer than ~2 minutes MUST be handed to the operator to execute — do NOT run it in-session.** This includes (non-exhaustive): backfills, `run_w1_lakehouse`/lakehouse rebuilds, full-history ingests, model fits / Optuna bake-offs, dbt `run`/`build` over many models, season-wide serving backfills, any box (`docker compose … exec`) job of real size. A quick smoke run on a TINY slice (1 date / a few rows / `--limit`) to prove the code path is fine and encouraged; the FULL run is the operator's.
**🖥️ DEFAULT A *DATA FIX* TO THE LAPTOP, NOT THE BOX (operator 2026-08-01, INC-37):** a lakehouse rebuild / backfill / re-export / re-score should be handed off as a LAPTOP command unless it needs box-only state. The box is an **r6g.large = 2 vCPU** and `run_w1_lakehouse` sets `SET threads=2` on every heavy build, so DuckDB alone saturates it: the INC-37 remediation tripped the `credence-box-cpu-sustained` CloudWatch alarm (95.5/99.5/90.4% over three 10-min periods) and, worse, **a pinned-CPU box can starve the Dagster daemon → sensors stop ticking (the INC-32 class)** — actively dangerous during an incident whose recovery depends on the lineup-monitor sensor. The laptop is also FASTER (measured: `mart_bookmaker_disagreement` 162.9s on the laptop vs >8 min on the box) and already has everything needed (same S3 via the `credential_chain` secret, AWS keys, `SNOWFLAKE_PRIVATE_KEY_PATH`) — just export `AWS_DEFAULT_REGION=us-east-2` for DuckDB-S3. ⚠️ Say plainly that a laptop run still writes **PRODUCTION** S3 keys. This does NOT relax the 🟥 RUNTIME GATE: validating a pipeline CODE change still requires the op to run once on the box.
**How to hand it off (mandatory format — the same as the session-closeout run-order rule):** give the operator (a) WHERE to run it — **LAPTOP or the EC2 BOX** (box commands wrapped in `docker compose -f services/dagster/aws/docker-compose.yml exec -T dagster-codeloc …`, `-e AWS_DEFAULT_REGION=us-east-2` for DuckDB-S3), and (b) the FULL, copy-pasteable command (exact flags/paths/env, no placeholders). Never silently kick off a >2-min job and wait on it.
- **🔬 MODELING BAKE-OFF DISCIPLINE (guide §0.5 — non-negotiable):** any story that BUILDS or SELECTS a predictive model runs a **bake-off, not a single architecture** — pre-register ≥3 candidate model classes, Optuna-tune each, feature-ablate, pick on the metric under purged/embargoed CV (per serving tier), guard the search with PBO<0.2/DSR>0. A prescribed structure is **one candidate among several**, always with a direct-learned foil. **A single architecture missing its gate is NOT a trustworthy null** — that's only earned after the whole candidate set, tuned + ablated, fails. Exemplar: E1.9 v6 (6 learner classes → Optuna → gate). Exceptions: pure registration/backfill, cheap sub-model re-eval, or explicit harness/eval stories.
  - **📏 SELECTION-METRIC HYGIENE (E2.1-r, 2026-07-20 — a pre-registered metric can be SILENTLY INVERTED):** ⚠️ **INTERVAL-COVERAGE TARGETS ARE BIASED FOR DISCRETE PREDICTIVES.** E2.1-r pre-registered `|calib_80 − 0.80|` — which LOOKS principled — but **inclusive integer interval bounds inflate a CORRECTLY-specified count model's coverage to ~0.82–0.86**, so the term **REWARDED UNDER-DISPERSION** and briefly ranked a genuinely under-dispersed candidate #1. **RULES: (a) for any DISCRETE/count predictive (runs, strikeouts, points, totals) gate on RANDOMIZED-PIT FLATNESS (e.g. max-decile-deviation), and keep a coverage figure as a FLOOR (`calib_80 ≥ 0.80`), never as a TARGET to minimize distance to; (b) ⭐ SANITY-CHECK EVERY SELECTION METRIC AGAINST AN ORACLE FLOOR** — score a known-correct oracle and assert nothing beats it (a candidate scoring BETTER than the oracle is mathematically impossible = the tell that the metric is inverted). Guard pattern: `test_oracle_is_the_scoring_floor`. Applies to E2.3/E2.4/E5.2 and the NCAAF/NFL totals legs.
    - **⚖️ (c) THE OTHER HALF OF THE ORACLE FLOOR = A DEGENERATE CEILING THAT MUST LOSE (NF-D11, 2026-07-29 — MAE is INVERTED on a zero-heavy cohort).** The oracle-floor catches "nothing should beat a perfect model"; it does NOT catch a metric a NIHILIST wins. NF-D11 selected a return-from-injury availability prior on a cohort where **43% of returners play ZERO games** — MAE is minimised at the conditional median, so it PAYS FOR PESSIMISM: a degenerate "project ZERO games for everyone" arm scored **MAE 15.47, BEATING the best real candidate's 18.96**. A metric a "predict nothing" arm wins cannot select a projection. **RULES: (a) for a zero-inflated / skewed cohort, use a PROPER score (CRPS) as primary — it grades point AND spread jointly, so pessimism doesn't win; (b) score TWO-SIDED anchors every run — the ORACLE FLOOR (knows realized outcomes, nothing beats it) AND a DEGENERATE CEILING (a trivial null — all-zero / all-mean — that MUST lose); a real candidate scoring worse than the degenerate = the metric is inverted.** MAE / RMSE on a zero-heavy or fat-tailed target is the smell.
      - **⭐ REFINEMENT (NF-D14, 2026-07-31 — the pre-registered inversion DID NOT FIRE, and knowing why matters): MAE inverts on the conditional MEDIAN, not on the zero ATOM.** NF-D14 pre-registered the NF-D11 inversion as CERTAIN (rookie QBs are zero-heavy too) — but the all-zero nihilist LOST MAE outright (5.96 vs 3.79). NF-D11's returners: 43% zeros AND **median 1 game** → the conditional median IS ~0 → pessimism wins. Rookie QBs: 31% zeros but **median 4 games** → the conditional median is positive → the nihilist loses. ⇒ **"zero-heavy" is NOT the test for MAE-inversion — the conditional MEDIAN being at/near the floor is. So don't REASON about whether MAE will invert; keep the degenerate ceiling in the field EVERY run and READ its score** (which is exactly why the rule is "score the degenerate," not "check if the cohort looks zero-heavy"). Applies to every zero-heavy/skewed §0.5 leg (E2.x totals/strikeout, NCAAF, prospect).
      - **📉 A DEFLATION STATISTIC COMPUTED OVER A FIELD CONTAINING ITS OWN NULLS MEASURES THE NULLS (NF-D14, 2026-07-31 — the NF1.8 whole-field-spread lesson, one statistic over, now on DSR).** NF-D14's whole-field **DSR 0.069 vs contender-set DSR 0.945** — because `deflated_sharpe`'s expected-max-SR term scales with the trial-Sharpe DISPERSION, and a field that includes its own pre-registered nulls has a huge dispersion that inflates the deflation penalty. **RULE: report BOTH the whole-field and the contender-set deflation stat (DSR/PBO), and pre-register WHICH binds** (NF-D14 bound the whole-field gate and STILL cleared under the generous reading, so nothing turned on the choice — that's the clean shape). Sibling of the NF1.8 "PBO over a field mixing near-clones with far nulls measures the nulls" lesson. Also from NF-D14: a winner can LEGITIMATELY beat a peeking oracle at UNMATCHED n (2.455 vs 2.977, the winner trains on ~500 rows vs the oracle's ~79 held-out) — the `matched_n_candidate` gate (NF1.9 (f)) is what makes that admissible, not a metric inversion; and a two-sided knob on an uncertainty covariate (an availability qreg FEATURE) is free to NARROW even when the widen-only widener is clamped (the NF1.7 (d) hazard on the channel the clamp doesn't cover).
    - **🪤 (d) FOUR WAYS AN ANCHOR SET LIES — the oracle floor / degenerate ceiling need these guards or they pass on nothing (NF1.7, 2026-07-29 — a §0.5 interval selection, all four hit + now guarded).** (1) **AN ANCHOR THAT FAILS TO FIT MAKES ITS CHECK VACUOUSLY TRUE** — NF1.7's per-position oracle refused a fit under 40 rows (a held-out class is ~80 rows / 4 positions → ~20 each), silently returned `None`, and `oracle_respected` passed on NOTHING. RAISE on a missing/failed anchor, never treat `None` as a pass. (2) **THE ORACLE FLOOR MUST BE SAME-FAMILY *AND* SAME-SAMPLE** — a peeking MISSPECIFIED oracle is legitimately beaten by an honest well-specified candidate, and a peeking k-NN's capacity depends on n (k=60 of 62 same-position rows = a constant band an in-fold arm beats). "peeking can only help" holds ONLY at equal family + equal resolution → for the UNIT test use a **PERMUTATION** (fit on truth vs SHUFFLED outcomes), well-posed at any n, not a fitted oracle. (3) **SHARPNESS NEEDS TWO DEGENERATES, NOT ONE** — `zero_width` (maximally sharp; a naive sharpness metric crowns it) AND `max_width` (coverage ~0.98, useless; a coverage-target loves it) must BOTH lose; reporting one leaves the metric gameable from the other side. (4) **A "WIDEN-ONLY" KNOB MUST ACTUALLY BE MONOTONE** — NF1.7's `exp(gain·z)` widener was two-sided → it SHARPENED half the field off a parameter-uncertainty z and cost coverage; clamp `z→max(z,0)` so it can only widen. ⭐ these apply to ANY interval/anchor-gated §0.5 story (E2.1-r/E2.3/E5.2/totals legs + any future NF/prospect interval).
    - **🕳️ (e) A ZERO-ATOM POPULATION MAKES A COVERAGE *TARGET* STRUCTURALLY INVERTED, AND CAN MAKE A CONFORMAL LAYER A MATHEMATICAL NO-OP (NF1.9, 2026-07-29 — the E2.1-r inversion in a NEW costume; ANY skewed/zero-heavy target).** NF1.9's veteran fantasy target has a **31% point mass at exactly 0** and a bound floored at 0, so the left tail is nearly un-missable (83% of lower bounds ARE 0; below-p10 0.025 vs nominal 0.10) → coverage ≈ 1 − P(y>p90) ≈ **0.89 for ANY honest band**, and a **0.80 coverage TARGET is INVERTED — hitting it requires deliberately UNDER-covering the RIGHT tail** (the pre-registered `normal_cov` arm prices that naive fix at +7.2% interval score). The SAME zero atom made NF1.8's *winning* Mondrian conformal layer a **no-op here** (~29% of conformity scores are exactly 0 → the (1−α) quantile pins at 0, all CQR arms score byte-identically to base). ⇒ on a zero-heavy / floored target, keep coverage a FLOOR (E2.1-r) and select on a proper INTERVAL SCORE (Winkler), and don't assume a mechanism that won on one population still ACTS on another — "a mechanism that cannot act is a finding, not an omission." Also: bigger σ was NOT the fix (score- and coverage-fitted normal arms both lost to a neighbourhood quantile that expresses a q10 genuinely 0 across the bottom deciles and positive in the top).
    - **📏 (f) A PEEKING ORACLE IS A FLOOR ONLY AT MATCHED n — OPERATIONALISE IT AS CODE, NOT PROSE (NF1.9).** The NF1.7 (b) lesson ("same-family AND same-sample") shipped as a runnable guard: the winner legitimately BEATS the peeking same-family oracle (160.9 vs 179.8) only because the oracle fits the ~646-row held-out season while the winner trains on ~7,236 — capacity, not leakage. NF1.9 adds a `matched_n_candidate` anchor (the winner's own arm trained on ONE prior season) and gates on the oracle beating THAT (179.8 ≤ 182.9), so the floor is enforced at equal family AND equal resolution. Reusable shape for any oracle-anchored §0.5 story.
    - **🎏 (g) A MATCHED FOIL SEPARATES A NULL FROM A TIE; A LEADERBOARD RANK CANNOT (NF-D10, 2026-07-31 — how a feature-family study earns an ATTRIBUTABLE "no").** NF-D10 tested a coaching-change feature family by registering EACH bundle beside the IDENTICAL bundle MINUS the new feature (`base_system_coach − base_xfp`, `env_coach − base_env`, `kitchen_sink − all_skill`) → the family was negative in 7 of 10 pairings and no position was positive on BOTH its pairs, so the lone positive (RB-sink +0.0229, contradicted by RB's other two pairs) was attributable to a contract/opp interaction, NOT the coach. **A leaderboard rank alone can't do this** — the best coach cell sat inside the top tie band at RB/WR (rank 4–5, ~1% back), which "it didn't win" reads as failure but the matched foil reads correctly as *indistinguishable-from-incumbent, not harmful*. **RULE: to earn an attributable null (or win) for a FEATURE/mechanism, register it as a matched pair (with vs without) and read the PAIRED delta, not the rank** — the rank confuses "my feature is inert" with "my feature is in a tie." (Sibling of the NF1.8 flip-distribution lesson: a rank statistic can't tell a tie from a loss.)
      - **🎏 (g′) A MATCHED FOIL ALSO REFUTES A *WINNER'S STATED MECHANISM*, NOT ONLY A NULL — and a level-vs-per-player claim has a bias SIGNATURE (NF-D15, 2026-08-01).** NF-D14 shipped a real lift and EXPLAINED it as a cold-bias LEVEL correction. NF-D15 registered the identical arm with its **per-player content stripped but the per-position MEAN scale byte-identical** (a matched level-only foil): the foil failed to beat the incumbent AT ALL (RB 87.33 vs 80.43, TE 55.49 vs 53.92) while the real arm beat that foil by 18.9/8.2 PPR (p=0.034/0.022) → the lift is PER-PLAYER, the stated level mechanism is REFUTED. ⭐ The corroborating tell a level story CANNOT produce: **the winner moved pooled bias FURTHER from zero (−20.87→−22.44) while MAE improved** — a genuine level correction moves bias TOWARD zero. **RULE: to attribute a WIN to its claimed mechanism (not just to earn a null), register a matched foil that keeps everything EXCEPT the claimed channel and read the paired delta + the mechanism's own signature (bias direction for a level claim); "my arm won" is not "it won for the reason I said." And a mechanism can be BOTH wrong-as-stated and real-as-a-separate-effect** — a per-position CONSTANT recalibration independently beat the incumbent (p=0.0052), a DIFFERENT effect from the per-player lift, so "the level story is refuted" ≠ "there is no level effect" (→ spun off pre-registered as NF-D16).
      - **📉 (g″) UNDERPOWERED ≠ ABSENT — a real effect can reproduce on the selecting metric, pass PBO, and STILL fail DSR/BH-FDR purely from n; the fix is a SCHEDULED re-run, not a ship, and the record must say so (NF-D15).** NF-D15's lift reproduced (draftable-tier MAE RB 80.43→68.44, TE 53.92→47.33), PBO was clean (0.029/0.057), the matched foil attributed it — yet it failed DSR (0.022/0.008) and the 3-test BH-FDR, so nothing shipped.     - **🚧 A COVERAGE FLOOR IS A CONSTRAINT AND MUST NEVER BECOME A TARGET — AND ITS PROOF IS THAT A DEGENERATE SATISFIES IT (NF1.8).** E2.1-r says a coverage figure is a FLOOR, never a target. ### 🧬 Type-contract guard (INC-19 — the NUMBER↔FLOAT incremental-drift cure) — ENFORCE
The recurring HALT class: a lakehouse dual-branch migration makes an upstream column compute as DuckDB DOUBLE→parquet→Snowflake FLOAT, but a downstream **`incremental` + `on_schema_change='sync_all_columns'`** table still stores it as `NUMBER(38,x)`; Snowflake can't ALTER NUMBER→FLOAT (`002108`) → the op HALTs and an operator must DROP+rebuild. Fired **5×** (INC-15 / W1d / INC-16-P0 / INC-19 / INC-19-recurrence), every victim = `feature_pregame_game_features_raw`.
- **CURE (prevention):** `feature_pregame_game_features_raw` wraps `final` in a generated `-- TYPE-PIN-START … -- TYPE-PIN-END` block that casts **every FLOAT output column to an explicit `::double`** (value-preserving 64-bit; `::float`=32-bit in DuckDB — never use it). The public wrapper `feature_pregame_game_features` casts each `_seasonnorm` column `::double`. So an upstream NUMBER↔FLOAT flip can never change the stored incremental type. The pinned set lives in `dbt/type_contracts/<model>.types.json` (**source of truth**).
- **GUARD (enforcement):** `betting_ml/tests/test_type_contract_guard.py` (fast gate) + `python3 scripts/gen_type_contract.py --check` (wired into the dbt-Build CI gate) go **RED** if a model's TYPE-PIN block drifts from its manifest.
- **🚨 CONVENTION — intended type change ⇒ update the contract in the SAME PR:** when you migrate a model / intend a type change, (1) edit the manifest (move a column in/out of `double_pinned`, or add/remove a column — re-derive truth from `information_schema.columns`), (2) `uv run python scripts/gen_type_contract.py --write` to sync the SQL, (3) commit model+manifest together (guard then passes). If a STORED type actually changed NUMBER↔FLOAT, the operator must **DROP+rebuild** the incremental (`--full-refresh` MERGEs, does NOT DROP — see [dbtf incremental note]). Add a new incremental victim to `CONTRACTS` in `scripts/gen_type_contract.py`. A new numeric column that can ever be FLOAT **must** be `::double`-pinned.
  - **➕ COLUMN ADD ⇒ `--full-refresh`; only a stored TYPE CHANGE ⇒ DROP+rebuild (E7.9, 2026-07-29 — a session called for an unnecessary DROP of two serving-critical incrementals).** For a model that is `delete+insert` / `on_schema_change='sync_all_columns'` (e.g. `feature_pregame_game_features_raw`), simply ADDING a column needs only `--full-refresh` — dbt's `ALTER ADD` already created the new columns at the correct type, no stored type flips, and `--full-refresh` avoids any window where the serving table is absent. **DROP+rebuild is required ONLY when a STORED column's type actually changes NUMBER↔FLOAT** (the INC-19 flip) — that's the sole case `--full-refresh`'s MERGE can't handle. Calling for a DROP on a mere column-add is unnecessary risk on a serving table. (Same session: a `--full-refresh`-less build silently ran only the 7-day incremental window — 116 of 1,637 rows — and went green; a column-add rebuild MUST be `--full-refresh` to touch all history.)

## Pipeline failure-handling contract (E11.7 — ENFORCE on every new op/test)

Three tiers govern how pipeline failures behave. Every new op, cron, sensor, and dbt test is assigned to exactly one tier:

| Tier | Behaviour | When to use |
|------|-----------|-------------|
| **HALT** | raise Exception / exit 1; fails the op/job | Serving-critical path only — `predict_today`, the feature store, serving-mart `dbt run`, the contract-guard, `write_serving_store`, signal freshness gate |
| **WARN-but-continue** | `context.log.warning(...)` + catch, op succeeds | Peripheral data-quality — non-serving ingestion (weather, OAA, bios), `dbt test` suite, user-bet settlement, narrative generation |
| **ALERT-loud-but-continue** | `context.log.warning(...)` or `echo WARNING` to stderr, then exit 0 | Any graceful skip that hides work — missing env var (DBT_RUNNER_URL unset), unreachable runner, no-op ingest; NEVER a silent `print()`/`pass` |

**Rules:**
- No in-process `dbtf` invocations anywhere — all dbt must go through `pipeline/ops/_dbt_exec._run_dbt` (enforces the remote-runner path and hard timeout).
- On `dbt build` days, the serving-critical step is always `dbt run` first (HALT on failure); the test suite is a separate non-blocking step (WARN tier). Never a single `dbt build` that gates predictions on a peripheral test failure (INC-6).
- Any `except` block in ops/sensor/cron files that does NOT call `context.log.warning()` (or write to stderr) is a contract violation.
- `dbt test` severity: serving-critical model contracts stay `error`; peripheral / non-serving data-quality checks use `severity: warn`.

## 🟥 RUNTIME GATE — CI-green is NOT a merge gate for pipeline/serving code (added 2026-06-29 after a string of merged-then-broke runtime bugs)
**The problem this fixes:** CI mocks ALL IO (Snowflake/S3/network) by design → the fast gate + `dbtf compile` CANNOT see the bug class that keeps biting prod — AKID credential-chain, the inline-Snowflake-key gotcha, INC-19 type-drift (only HALTs on a real incremental run), INC-20 OOM, INC-21 (sensor silently not firing), INC-22 (UTC-date). Every one is a RUNTIME / box-environment bug invisible to CI. So "CI green" is necessary-NOT-sufficient and must NOT be treated as "ready to merge" for this code class.
**THE RULE:** for any change touching the **daily pipeline / serving writers / S3 exporters / sensors / ops / date-or-tz logic / boto3 / DuckDB-on-box**, the merge bar = **CI green AND the relevant op actually RAN once on the box** (a scoped run is fine — you do NOT need the full 40-min pipeline; skip the stable W1 pitch rebuild and run only the targeted chain, per the INC-21 recovery). ⚠️ flag-gated dual-branch code is safe merged-OFF (Snowflake arm stays live), but the **un-gated runtime glue runs regardless of any flag** (that's how INC-21/INC-22/AKID hit prod despite cutover flags being off) → that glue is where the real-run gate matters MOST.

Repoint + parity-check the HISTORY-SPANNING readers (the parity gate's `only_in_sf` bucket = the consequential one: those keys lose their seed and get skipped). Two corollaries: (a) tables whose reads are UNIONed into one DERIVED MAP must move together (a derived map needs a single vintage, or a row's value depends on which side carried a ghost); (b) ⛔ `enabled=false` is NOT the cleaner end state until EVERY reader is repointed — a disabled model makes `ref()` unresolvable while DROPping nothing, so the relation lingers as a TABLE NOBODY REBUILDS (the silent-staleness bomb); a VIEW is the safe shape until then.
- **🏷️ A `served_*`-NAMED COLUMN ON A RESEARCH PANEL DOES NOT TRACK THE SERVING ARTIFACT — the "documented ≠ actually served" class, one level down (NF1.9-R, 2026-08-08):** NF-RECAL1's C3 gate read "the incumbent band" from a veteran panel's `served_p10`/`served_p90` columns — which `VET_PANEL_COLS` documents as "the LITERAL emitted PRE-NF1.9 band" (frozen so NF1.9's incumbent arm stays reproducible; they never tracked what shipped AFTER). So a gate named its bar off a column called `served_*` that is NOT the served band → C3 refused every level-recal arm against a `min(0.80, 0.50)` bar built on the WRONG band, when the band actually on the wire covers **0.845** on the tier. RULE: any gate needing "the incumbent/served band" must REFIT the current served config through the model path and PROVE which band it holds by reproducing a recorded SERVED figure — never trust a `served_*` COLUMN NAME on a research/panel table. Consequence carried forward: NF-RECAL1's + NF-D21's C3 refusals were computed against the wrong band ⇒ a PM re-read is owed (the direction says the corrected bar is STRICTER, so the refusal most plausibly stands — but that's a reading, not a measurement).
- **🚰 A VIEW-FLIP MOVES WAKE, IT DOESN'T DELETE IT — WAKE IS A QUEUE, NOT A SUM (E11.24 #679, 2026-08-08):** on an auto-suspending warehouse only the FIRST occupying statement after a suspend pays the resume; making it metadata-only (a `table`→`view` flip) PROMOTES the next statement in the same run to pay the resume instead. Measured: flipping the umpire/lineup CTAS moved 5–7 waits/day onto EB-posterior merges that had run for six days at ZERO waits, executions unchanged, total resumes FELL. ⇒ (a) a single flip in a build chain does NOT reduce the bill by itself — reaching literal-zero needs the WHOLE chain flipped, one-per-soak, and the wake WALKS DOWN THE LIST as you go (budget for N soaks); (b) size a flip's payoff by the wake it MOVES vs the wake that DISAPPEARS — only a flip whose successor is ALSO metadata-only (or lets the warehouse suspend) actually deletes wake. Verify a wake reduction by the warehouse SUSPENDING on a zero-game window, not by one statement's waits hitting 0.
- **🕳️ `warehouse_size IS NULL` MEANS THE QUERY NEVER OCCUPIED THE WAREHOUSE — awake-TIME attribution MUST filter it out; WAITS are immune (E11.24 #679, 2026-08-08):** cloud-services-billed statements — `SHOW`, `ALTER SESSION SET QUERY_TAG`, `ALTER EXTERNAL TABLE … REFRESH`, `CALL SYSTEM$…`, and EVERY `create or replace view` — can neither RESUME nor KEEP the warehouse awake, yet are 40–138% of a naive awake-minutes figure (a first cut ranked a Snowsight browser poll as the account's largest awake-time consumer = a phantom that would send a fix session at nothing). Filter awake-time on `warehouse_size IS NOT NULL`; a provisioning-WAIT is safe (a wait implies a real occupation). And the recurring companion: the AGGREGATE lies across a flip date (a 6-day window put an already-flipped view at the top of the wait board; per-day showed it 0) — only the PER-DAY cut is quotable.
- **🧪 A RED-PROOF HARNESS MUST ASSERT ITS MUTATION ACTUALLY LANDED BEFORE RUNNING THE TEST — a RED-proof that can silently NO-OP its own break reports a FALSE "the guard caught it", and it reads as a finding (E11.24 #682, 2026-08-08 — the vacuous-guard class one level up):** a first-cut RED-proof shelled out to apply deliberate source breaks and reported 2 guards "green on broken source" (read as a real defect) — but a shell-quoting bug meant the MUTATIONS NEVER LANDED, so the test passed because the source was UNCHANGED. RULE: a RED-proof must apply its mutation IN-PROCESS (or diff the file) and ASSERT THE SOURCE ACTUALLY CHANGED before invoking pytest — otherwise "the deliberate break went red" and "the break never happened" are indistinguishable, and the latter reads as the scarier (false) finding. (INC-38's prose-cannot-satisfy / NF1.7(a) vacuous-anchor, applied to the test-of-the-test.)
